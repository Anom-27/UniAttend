\hypertarget{abstract}{%
\subsection{1. Abstract}\label{abstract}}

Most universities still record class attendance on paper sheets. Sheets
get lost, totals are calculated by hand, students cannot check their own
record, and corrections leave no trace. UniAttend replaces the paper
sheet with a centralized web application where teachers record
attendance per class, students monitor their own percentage, and
administrators manage courses and departmental reports. Every class and
every correction is stored permanently.

\hypertarget{problem-statement-and-objectives}{%
\subsection{2. Problem Statement and
Objectives}\label{problem-statement-and-objectives}}

Manual attendance causes slow reporting, calculation errors, proxy
marking, no audit trail and no early warning for students at risk. The
objectives are:

\begin{itemize}
\tightlist
\item
  Let teachers take attendance for a class in under one minute.
\item
  Calculate attendance percentage automatically and correctly.
\item
  Give each student a private view of their own record and warnings.
\item
  Keep a permanent history of every class and every correction.
\item
  Give administrators department-level reports.
\end{itemize}

FR13 & The attendance sheet shows each student's nickname and ID;

attendance summary. \\
FR14 & A nickname has 2 to 20 characters and is unique within a
course. \\
FR15 & Passwords are stored only as salted hashes in the database (users
table). A password needs at least 8 characters with a letter and a
number, and 5 wrong attempts lock the account for a minute. \\
FR16 & Forgot password: the user enters the university email, receives a
6-digit reset code (valid 10 minutes, limited tries, single use) and
sets a new password. The reply never reveals whether an email is
registered. \\
FR17 & Student IDs are always listed in order, newest batch first and
then by number (IT24001, IT24002, \ldots, IT23001, \ldots), whatever
order students join. The ID is added automatically from the university
email, so nobody types it. \\
FR18 & On a desktop browser the teacher can take attendance with the
keyboard: W or Up arrow and S or Down arrow move the highlighted row,
and Enter switches Present and Absent. The active row is highlighted
automatically. Phones and tablets use touch. \\
FR19 & The admin manages a university directory (email and full name). A
student can join a course only if the email is in the directory, and the
full name is taken from it. In the real system the directory is replaced
by the university account (OAuth sign-in). \\

\hypertarget{non-functional}{%
\subsubsection{Non-functional}\label{non-functional}}

\begin{itemize}
\tightlist
\item
  \textbf{Security:} passwords stored only as salted hashes (bcrypt in
  the real system), account lockout after wrong attempts, password reset
  by a one-time emailed code, role-based authorization, students cannot
  edit records.
\item
  \textbf{Reliability:} data stored in a relational database with
  regular backup.
\item
  \textbf{Usability:} a 50-student sheet can be completed in under one
  minute; works on phone screens.
\item
  \textbf{Performance:} a page loads in under 3 seconds for 500
  concurrent users.
\end{itemize}

future-date rule and permission checks. Integration tests for login and
attendance save. User acceptance testing with one teacher and a few

\hypertarget{interface-prototype}{%
\subsection{12. Interface Prototype}\label{interface-prototype}}

The prototype implements eight classes from the class diagram in
JavaScript (with email and password login, forgot password, class
duration of 1 to 5 hours counted as hours, keyboard attendance on
desktop, sorted student IDs, a student timeline of hour squares,
nicknames, and the full name collected automatically from the university
account): \texttt{User}, \texttt{Student}, \texttt{Teacher},
\texttt{Course}, \texttt{ClassSession}, \texttt{AttendanceRecord},
\texttt{AttendanceService} and \texttt{AuthService}. It demonstrates
taking attendance, history, correction with an audit log, the percentage
rule, the student warning and the admin report. Open the prototype.
Prototype data is saved in the browser's localStorage only (it works
across tabs of one browser, and is not a database); the full system
stores it in MySQL.

\hypertarget{feasibility-study}{%
\subsection{13. Feasibility Study}\label{feasibility-study}}

\begin{longtable}[]{@{}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.1728}}
  >{\raggedright\arraybackslash}p{(\columnwidth - 2\tabcolsep) * \real{0.8272}}@{}}
\toprule\noalign{}
\begin{minipage}[b]{\linewidth}\raggedright
Area
\end{minipage} & \begin{minipage}[b]{\linewidth}\raggedright
Finding
\end{minipage} \\
\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot
Technical & The stack (HTML, CSS, JavaScript, Java with Spring Boot,
MySQL) is mature, free and well documented. The core rules
(hour-weighted percentage, corrections, join link, login) are already
working in the prototype and covered by 26 automated tests. The main
technical risks are learning Spring Boot and Spring Security and
integrating university sign-in. Both are reduced by building in small
increments and by keeping email and password login as the first
version. \\
Economic & Development tools (VS Code or IntelliJ Community, Git,
GitHub, MySQL Community, Mermaid, PlantUML, LaTeX) are free. The only
running cost is hosting for the backend and database: a university
server or a low-cost cloud plan (assumed budget of up to BDT 2,000 per
month after deployment, to be confirmed). The benefit is saved teacher
time, fewer calculation errors and a record students can trust. \\
Operational & Teachers already take attendance every class, so the new
steps are small: pick duration, mark students, save. The join link
removes manual entry of student IDs and names. Students only sign in and
read. Keyboard shortcuts speed up large classes on desktop. \\
Schedule & About 8.5 weeks are planned (20 Oct to 20 Dec 2026) with an
incremental model. Version 1 is limited to attendance, history, student
view, login and the join link, so the plan fits one developer. \\
Legal and privacy & The system stores student names, IDs, emails and
attendance. Passwords are stored only as salted hashes, access is
role-based, and every correction is logged. The system must follow the
university's data protection and privacy rules, and exam eligibility
stays a university decision. \\
\end{longtable}

\textbf{Conclusion:} the project is technically, economically,
operationally and schedule-wise feasible for version 1.

\hypertarget{assumptions-constraints-and-dependencies}{%
\subsection{15. Assumptions, Constraints and
Dependencies}\label{assumptions-constraints-and-dependencies}}

\textbf{Assumptions}

\begin{itemize}
\tightlist
\item
  Every student, teacher and admin has a university email address.
\item
  Classes last 1 to 5 whole hours and the default minimum attendance is
  60\%, configurable per course.
\item
  Users have a modern desktop or mobile browser and internet access.
\item
  Teachers use a desktop computer for the keyboard shortcuts; phones use
  touch.
\end{itemize}

\textbf{Constraints}

\begin{itemize}
\tightlist
\item
  One developer, fixed deadlines, free or low-cost tools.
\item
  The software records attendance and calculates percentages only. The
  university policy decides exam eligibility.
\item
  No integration with the university ERP in version 1.
\end{itemize}

\textbf{Dependencies}

\begin{itemize}
\tightlist
\item
  Access to the university account list or sign-in (the prototype
  simulates it with an admin-managed directory).
\item
  A server or cloud account to host Spring Boot and MySQL.
\end{itemize}

\hypertarget{quality-assurance-and-configuration-management}{%
\subsection{16. Quality Assurance and Configuration
Management}\label{quality-assurance-and-configuration-management}}

\begin{itemize}
\tightlist
\item
  \textbf{Version control:} Git and GitHub, small commits with clear
  messages, one branch per increment, merged only after the tests pass.
\item
  \textbf{Testing:} unit tests for business rules (already automated),
  integration tests for the API, and user acceptance testing with a
  teacher and students.
\item
  \textbf{Definition of done:} a feature is complete when it meets its
  requirement (FR numbers), has tests, passes them, and is documented in
  the README.
\item
  \textbf{Change control:} requirement changes are recorded in the
  proposal and traced to tests and diagrams.
\item
  \textbf{Security checks:} hashed passwords, lockout after wrong
  attempts, role checks on the server, no sensitive data in the
  repository.
\item
  \textbf{Backups:} regular database backup after deployment.
\end{itemize}

\hypertarget{conclusion}{%
\subsection{17. Conclusion}\label{conclusion}}

UniAttend is a realistic and extendable project. Version 1 delivers the
three most valuable features first, and later increments add the real
backend, admin tools and reports. Future ideas include QR-based
check-in, risk prediction for students near the minimum and
excused-absence requests.
